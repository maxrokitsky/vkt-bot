# Напоминания

План реализации: пользователь пишет в чат `!напомни <время> <текст>`, бот
подтверждает, а в назначенный момент пишет в тот же чат и упоминает автора.

Составлен 2026-09-10 по итогам разбора текущего кода. Связанные документы:
[CLAUDE.md](CLAUDE.md), [ROADMAP.md](ROADMAP.md), [EVENTS.md](EVENTS.md),
[TODO.md](TODO.md) (раздел «Напоминания»).

---

## Сценарий

```
Пользователь:  !напомни завтра в 10:00 позвонить в банк
Бот:           @[user], напомню 11.09.2026 в 10:00 (через 21 час):
               «позвонить в банк»          [Отменить]

…через сутки…
Бот:           @[user], напоминаю: позвонить в банк
```

Работает в личке, в группе и в обсуждении: у треда собственный `chatId`, но
`messages/sendText` и упоминания `@[user_id]` там доступны.

## Решения по умолчанию

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Префикс команды | `!напомни`, синонимы `напомнить`, `remind` | `CommandFilter.COMMAND_PREFIXES` уже содержит `!`, `.`, `/`; `CommandHandler.check` берёт слово после префикса — кириллица проходит без правок фреймворка |
| Разбор времени | свой парсер, без `dateparser` | нужны точные сообщения об ошибке и жёсткая граница «время / текст напоминания»; fuzzy-парсер съел бы часть текста («в 5 утра позвонить **1 октября**») |
| Часовой пояс | глобальный: `TIMEZONE` в `.env` (по умолчанию `Europe/Moscow`), переопределяется ключом `timezone` в `bot_settings`; в строке хранится tz, в котором напоминание завели | персональные пояса — отдельная фича; без колонки `tz` повторяющиеся напоминания сломаются на переводе часов |
| Кому напоминать | только автору команды | напоминания другим — спам-вектор, нужна отдельная проработка прав |
| Повторяющиеся | не в первой фазе, но модель к ним готова (`repeat_rule`, `next_at`) | иначе схему пришлось бы менять второй миграцией |
| Где крутится планировщик | процесс бота (`main.main`), рядом с `retention_task` | если поднять его ещё и в `server`, каждое напоминание уйдёт дважды |

## Форматы времени

```
через 5 минут / через 2 часа 30 минут / через 3 дня / через неделю
5м, 30мин, 2ч, 1д, 2ч30м            — короткая форма без «через»
в 15:00 / в 9 / в 15.30              — сегодня, а если уже прошло — завтра
сегодня в 18:00
завтра / завтра в 10 / послезавтра в 9:30
в понедельник / в пн в 10:00         — ближайший такой день недели
12.09 в 10:00 / 12.09.2026 18:00
1 октября / 1 окт в 9:00
утром / днём / вечером               — 09:00 / 13:00 / 19:00
```

Правила:

- дата без времени — `reminders_default_time` (10:00);
- время без даты, которое уже прошло, — следующий день;
- «в пн», сказанное в понедельник, когда время ещё впереди, — сегодня;
- всё, что осталось после разобранного префикса, — текст напоминания;
- пустой текст допустим, пустое время — ошибка со списком примеров.

Ограничения: горизонт ≤ 1 год, минимум 10 секунд, текст ≤ 1000 символов,
≤ 50 активных напоминаний на пару «пользователь + чат».

Отдельный пункт: `src/vkt_bot/db/types.py` с `UtcDateTime(TypeDecorator)`
поверх `sa.DateTime(timezone=True)` — на запись приводит к UTC, на чтение
возвращает aware. Без него PostgreSQL отдаёт aware, SQLite — naive, и тесты
разойдутся с продом на сравнении `remind_at <= now`.

Миграция: `uv run alembic revision --autogenerate -m "reminders"`, файл
вычитать — autogenerate не увидит `TypeDecorator` красиво.

## Разбор времени

`src/vkt_bot/core/reminders/parser.py` — чистая функция без БД и сети:

```python
def parse(text: str, *, now: datetime, tz: ZoneInfo) -> ParseResult
# ParseResult: remind_at (UTC) | None, body: str, error: str | None
```

Набор регекспов, каждый съедает свой префикс. `now` и `tz` — аргументы, чтобы
тесты не зависели от системного времени. Это самая тестируемая часть работы:
таблица примерно из шестидесяти случаев.

Попутно чиним `src/vkt_bot/utils/datetime.py`: `now()` сейчас падает
(`datetime.datetime()` вызывается без аргументов), дефект зафиксирован тестом
`tests/utils/test_utils.py::TestNow::test_is_broken` — его надо переписать на
нормальную проверку.

## Хендлеры

`src/vkt_bot/core/handlers/reminders.py` (плюс импорт в `handlers/__init__.py`):

- `CreateReminderHandler(CommandHandler)` — `commands = ["напомни",
  "напомнить", "remind"]`. Разбирает время, проверяет лимиты, пишет строку,
  `emit(REMINDER_CREATED)`, коммит, отвечает подтверждением с inline-кнопкой
  «Отменить» (`ReminderCancelCallbackData` в `handlers/callback.py` по образцу
  `DeleteRoleCallbackData`: в ней `reminder_id` и `requested_by`, чужую кнопку
  не нажать).
- `ListRemindersHandler` — `!напоминания`: активные напоминания автора в
  текущем чате, с id и локальным временем.
- `CancelReminderHandler` — `!отменинапоминание <id>`: только своё, админ —
  любое в чате.
- `CancelReminderConfirmation(BotButtonCommandHandler)` — обработка кнопки,
  `edit_text` подтверждения на «Напоминание отменено».
- `!напомни` без аргументов отвечает справкой по форматам.

Логика создания и отмены живёт в `core/reminders/service.py`, чтобы панель
(см. «За рамками первой фазы») переиспользовала её, а не дублировала.

## Планировщик

`src/vkt_bot/core/reminders/scheduler.py` по образцу
`core/events/retention.py`:

```python
async def fire_due(session, bot, *, now) -> int   # одна итерация, тестируется напрямую
async def run_scheduler_loop(bot) -> None
@contextlib.asynccontextmanager
async def reminders_task(bot): ...                # в main.main рядом с retention_task
```

- **Захват батча:** `UPDATE reminders SET status='sending' WHERE id IN (SELECT
  id … WHERE status='pending' AND remind_at <= now ORDER BY remind_at LIMIT
  100) RETURNING *`. Работает и в PostgreSQL, и в SQLite ≥ 3.35: при случайном
  втором процессе бота напоминание не уйдёт дважды.
- **Сон:** `min(30, max(1, до ближайшего remind_at))` — точность до секунды для
  близких напоминаний, не больше 30 секунд в худшем случае, без busy-loop.
- **Отправка:** `mention(user_id)` плюс текст, обычным `send_text` в `chat_id`.
  Без `reply_msg_id` и `forward_*`: в обсуждениях API их отклоняет
  (`Bad request`).
- **Проверка ответа:** `MsgResponse.ok` — при `ok: false` исключения не будет.
  Отказ увеличивает `attempts` и возвращает строку в `pending` с отсрочкой
  (1, 5, 15 минут), после пяти попыток — `failed`, событие уровня WARNING и
  попытка сообщить автору в личку («не смог напомнить в чате X»).
- **Просрочка после простоя:** напоминание всё равно отправляется; если
  опоздали больше чем на 10 минут, к тексту добавляется «(напоминание
  просрочено, было на 10.09 в 18:00)» — молча врать про время хуже, чем
  признаться.
- Любое исключение внутри итерации логируется и не роняет цикл.

## Подводные камни

- **Двойной запуск.** `uv run server` не должен поднимать планировщик — он
  живёт только в `main.main`. При нескольких репликах бота защита есть только
  на уровне захвата батча; полноценная блокировка (advisory lock) — если такое
  появится.
- **Бота выгнали из чата** к моменту срабатывания: `ok: false`, строка уходит в
  `failed`, автор получает сообщение в личку.
- **`ChatUser` может не существовать** — `get_or_create` перед вставкой, иначе
  падает внешний ключ.
- **Время в БД** — всё в UTC, `tz` только для показа и повторов. Шаг 0 не
  пропускать.
- **Кириллическая команда с запятой сразу после** (`!напомни, …`) в текущий
  `CommandHandler.check` не попадёт: либо обрезаем пунктуацию при разборе
  команды, либо смиряемся.
- **Тайпчекера в CI нет** — ошибки сигнатур ловятся только тестами.

## За рамками первой фазы

- Повторяющиеся напоминания (`каждый день в 10:00`, cron-подобные правила).
- Напоминания другим участникам и по роли (`!напомни #дежурный`).
- «Напомни про это» в ответ на сообщение — якорь `source_msg_id` уже есть.
- Персональные часовые пояса.
- Раздел в панели: `/api/reminders` плюс `make generate_client`.
- Отложенная отправка сообщений («Планировщик сообщений» из `TODO.md`).
